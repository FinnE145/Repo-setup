# Firmware lessons

Read by the phases in repos with the `firmware` module, the parts that touch the work at hand — never every turn. Distilled from desk-bridge's dashboard (an ESP32-S3 RGB display with LVGL 9, a Pico 2 input module on I2C, a Windows laptop host, a USB macropad hosted on the Pico over PIO-USB, an I2S speaker), 2026-10-13 to 10-28. Board-specific facts belong in the repo's `docs/firmware/board-notes.md`, not here.

## Display and LVGL
- **A page change paints top to bottom when LVGL renders tile by tile straight onto the panel.** Rendering the whole change into one full-size PSRAM buffer (direct render mode) and copying the changed rows to the panel's framebuffer in one go makes it appear complete, at the price of a tap being answered about 30 ms later. Use one buffer, not two: with two, LVGL also copies every change into the spare. Write back only the rows copied, not the whole framebuffer. Keep it behind a flag so the two can be compared by eye.
- **With no LVGL theme every object starts bare**, so one helper that strips styles, scrolling and clicking, and a few for labels, icons and round buttons, keep the screens short. A label that must end in "..." needs a fixed height as well as a width, or it wraps instead.
- **A pressed child object does not pass the press to its parent**, so decoration inside a tappable object is made non-clickable.
- **Only set what changed.** `lv_label_set_text` and style setters invalidate even when the value is the same; wrapping them to compare first keeps redraws to what actually changed.
- **A highlight made by changing an object's fill is painted over by any refresh that sets the same fill**: the compare-first helpers write the base colour back. Re-apply the highlight after every refresh, or draw it on an object nothing else touches. (A border-based ring has the opposite flaw: LVGL borders take layout space and shift the content a couple of pixels, which wrecks small icons. An outline would not shift anything.)
- **A frame for a lit fill must sit under the content.** A bare overlay made after the content hides it when lit; make it the first child so the fill is drawn first.
- **Rounded text and icon assets without installing anything:** a font can come from the LVGL repo's own TTF drawn by Tiny TTF at any size from one embedded array, and alpha-only icon bitmaps can be made from SVG with a small numpy rasterizer (flatten curves and arcs, even-odd or nonzero fill, supersample). One weight only, so "bold" has to be faked by drawing text twice a pixel apart or by colour.
- **A touch panel library's rotation constants may not mean what they say**: check all four corners with a throwaway screen before building on it (one library's "normal" mirrored both axes).
- **State held for "the open popup" must be set and cleared on every path that opens or closes one, not only the obvious one.** The pager was reset in `open_popup` and `close_popup`, but three other openers set the popup directly; a mutation that removed a redundant guard survived, and that is what showed the other openers. One `clear_pages()` called from each opener, with a test that opens each over a paged row. Likewise every way a popup can close should drop its timer, so the timer needs no check of its own (a first draft re-checked "is this still the popup" on every tick, and half of it was unreachable).
- **A UI built once into module statics is cheaper to update in place than to rebuild.** Build the maximum of whatever varies in number (rows), lay out the number in force at each refresh, keep a preset button's slot as its event data instead of its value, and register the fills made with a changing colour so one call recolours them; everything coloured at refresh picks the new value up by itself.

## USB and the host
- **A host's sleep is not visible on USB by default.** A laptop with Modern Standby kept the USB bus running through standby on AC, and suspended it only after about 46 s on battery. Measure on the real host, on battery and on the charger, for minutes rather than seconds. A tiny helper on the host listening for display off/on was instant on every path.
- **Watch the bus, not only the stack's flags.** Logging the USB frame counter directly (it advances every 1 ms while the host runs the bus) separated "the host kept the bus up" from "the stack didn't report it".
- **A USB device being unplugged or plugged in looks like a sleeping host for a moment.** Pulled out, the device lived a few milliseconds more and saw its bus go quiet (longer on a slow pull: the data pins break before the power pins); plugged in, it was unmounted until the host set it up, about 2 s. Read the host's sleep from USB only after it has held for a few seconds, and give a faster signal (a host helper) its own path.
- **A Windows serial handle kept open can go dead silently** when the device re-enumerates (reflashed, replugged): writes still succeed and nothing arrives. Reopen it periodically. Opening it on demand instead was too slow at Modern Standby entry: Windows froze the process before the line went out.
- **An app holding the device's port stops the upload** from resetting it into the bootloader ("No drive to deploy"). Stop it first, or use the bootloader button.
- **The board's serial port moves** between USB ports: list the boards before every upload. Opening the port may reset the board.
- **A USB host bit-banged on PIO needs a CPU clock that is a multiple of 12 MHz** (120 MHz on the RP2350, whose default is 150). Measure it in plan: it changes the build options of a sketch that already works.
- **An output report sent from the mount callback was refused**; the same report sent later from the loop completed. Send anything to a newly mounted device once its mount has finished.
- **A request counted as done when it was queued, not when it completed,** leaves the device wrong until the next change if the transfer fails on the wire. Use the completion callback.
- **Reflashing a USB host reboots what hangs off it.** The macropad came up with its lights on until the Pico mounted it and set Num Lock, so each upload at night was a visible flash. Count uploads as visible events when someone is asleep in the room.

## Wiring and power
- **Pin labels on the underside mirror the columns.** "Left" and "right" flip between the person reading the labels and the person counting from the top. Give wiring by label or by a printed corner mark; a photo of the wiring finds the mistake at once.
- **A reset on a button press is a wiring clue**: the switch is on a reset or enable pin (RUN, on a Pico). Check the uptime after each test: a small one means the device restarted.
- **Dual power needs its own diode.** Powering a dev board from a rail and its USB at once usually needs a Schottky diode on the rail's side: the board's built-in diode protects only its own USB port. Check the board's datasheet before calling it safe (a session got this wrong).
- **On a shared bus, send cumulative counters, not events.** A dropped or corrupt read then loses nothing: the next good one carries the difference. And test that the new device unpowered doesn't hold the bus down.
- **A header pin labelled "5 V" may be a sense line, not a supply.** The board's serial header has a "5 V" pin that reaches the rail through 10 kΩ and a FET; wired to the Pico's VSYS it ran nothing. Read the pin's net in the schematic before planning to draw power from a header. Without a meter, a device that only turns on with power (here the Pico, shown by the board's "connected" state) is a better indicator than one that may stay dark without a host (the macropad's lights).
- **A USB-A source needs no CC resistors on a USB-C receptacle breakout**, a USB-C source does (5.1 kΩ to ground); picking the charger's port can save a part.
- **Run the hardware checks in the order that finds damage first.** The "no backfeed" check ran before the "both sources" one, so a backfeed would have shown with one source, not two.
- **Two outputs on one wire: the stronger driver decides what the wire carries.** Lowering the S3's drive strength to "fight less" made the other chip win and turned the audio clock to noise. When a shared pin can't be avoided, keep the signal that must be clean at the stronger drive and keep the fight short.

## Sound
- **An always-on I2S amp pops when its clock starts or stops**, and fading the samples doesn't help. Keep one clock running for a whole sound event and play silence in its gaps.
- **Sound choices go faster as rounds of numbered candidates played back to back** with the person listening: each round a short list, then ask which. Loops need whole bars on a beat grid: a fixed gap between repeats sounded "a tiny bit late".
- **Every sound in a probe is a serial command, none on boot**, so a reset or a flash never plays anything before the person at the board has said go.

## Debugging a hang
- **A bit-banged USB host can hang in a way the wiring only seems to explain.** The second core stopped looping within a minute with loose jumpers, and after 2 to 4 minutes with a twisted pair and pull-downs; the other core carried on, so the device looked half alive. Better wiring only made the real fault (a software race, below) rarer, by cutting retries. When a hang's timing depends on wiring or load, suspect a race whose odds those change.
- **Ask a stuck core where it is instead of guessing.** On a dual-core MCU, have the healthy core force an interrupt that only the stuck core enables, at the highest priority; a naked handler reads the hardware-stacked frame (`tst lr, #4` picks MSP or PSP; PC at word 6, LR at 5, xPSR at 7, whose low 9 bits name the exception that was running). One sample at boot proves the instrument; eight at the stall show a loop as the same one or two addresses. No answer at all means interrupts masked or a fault. Map addresses with the toolchain's `addr2line` and `objdump` on the build's `.elf`. This found in one run what a day of wiring changes didn't (a loop counter and a "where am I" marker had said "inside the library's task", which was wrong: an interrupt had preempted the task and never returned).
- **Polling for a transient state with no timeout is a hang waiting for a busy bus.** The library waited for a PIO state machine's program counter to pass through a value it holds for 170 ns, then never again; once in many thousand packets the CPU looked late and spun forever, inside an interrupt. Every wait on hardware gets a bound, even one that "always" ends in nanoseconds.
- **Bounding one wait can move a hang instead of ending it.** The first patch's 3 µs give-up returned while the USB device was already answering, and the next wait on the same path then spun forever on a flag the answer raised again. After bounding a wait in an interrupt path, list every other loop that path reaches and ask what state each give-up leaves for the next one.
- **"Clear a flag, then wait for it to read clear" is unbounded whenever hardware can raise it again in between**, and how often that happens depends on timing elsewhere. Bound it, and count the give-ups.
- **Count each give-up and log the count.** It shows the bound is reached, how often (here about three a minute), and that the system ran on afterwards, which a clean soak alone can't tell apart from the race just not happening.
- **Soak by reading the device's own log, not by watching a light.** A soak the spec guessed at 10 minutes found its answer in seconds once the log was read from the laptop, and a 3-minute run was enough; the Windows serial reader needed a reconnecting loop because the device re-enumerates after each upload.
- **A task's configured priority is not its priority while it holds a lock a higher one waits for.** esp-mqtt's task, set to 1, ran its whole TLS handshake at 23, inherited from the Wi-Fi task, on the loop's core, while the other core idled. Read the current and the base priority (`uxTaskGetSystemState`) before tuning one; lowering the task's priority changed nothing.
- **On ESP-IDF's (non-SMP) FreeRTOS an unpinned task can't be pinned after it is created** (no `vTaskCoreAffinitySet`), and a precompiled library's Kconfig choice (`CONFIG_MQTT_TASK_CORE_SELECTION_ENABLED`) can't be turned on from a sketch. Check the core's `sdkconfig` before planning on either.
- **To find what holds a loop, sample the scheduler from the other core:** a task pinned there at a high priority that notices the loop has gone quiet and prints every task's state, priorities, core and run time. Run time is credited only at a switch-out, so a task still running shows nothing for the window; take the baseline once the stall has begun and compare against wall time.
- **A sampler that walks every task often can be seen on the panel.** `uxTaskGetSystemState` every 20 ms made an RGB panel with a bounce buffer jitter; taking it only once a stall had begun stopped it. Keep debug probes off the hot path, and believe the person watching the screen.
- **Ask what a fix costs in the common case before proposing it.** Raising the loop's priority for good would have traded a rare stall (a wrong password) for a permanent delay to the event task; the narrower version (only during connect attempts) was the honest offer, and Finn chose to accept the stall instead.

## Behaviour over time
- **A fallback for "the other side is gone" must ride through the other side's normal stalls.** The board's failed TLS logins stalled its loop past the Pico's 500 ms read timeout every 10 to 30 s, and each gap flashed the pad's lights in a dark room. Keep the last state for a named time before falling back.
- **State printed only when it changes is lost to whoever opens the port later.** A host helper held the port while a bench check failed, so the `host stalled` line went nowhere. Print the current state when a reader opens the log.
- **A "fast spin" or any gap-based rule needs the first event of a call to be timed against the last call, and the rest of the call to count as close.** An encoder poll can deliver several detents at once, and tests that feed one detent per call never meet that case.
- **A level-driven controller (reconcile what the state wants against what the server has, on every pass) beat an edge-driven one**: a hand change is one flag that stops the reconciling, and renewal and expiry fall out of the same comparison. The trap was the wall clock passing the old end a moment before the counter saw the phase end, which had to be kept from expiring the state in between.

## Toolchain and libraries
- **Patching a third-party Arduino library: copy it into the repo, build it with `--library`, and make the sketch refuse the unpatched one** (a marker macro in the patched header and an `#error`), so a build that forgets the flag fails instead of shipping the bug. A note beside the copy says what changed and why.
- **A header reached by two spellings of its path is two files to this toolchain.** `#include "config.h"` (found via the sketch folder) in one header and `"../../config.h"` in a UI file made the ESP32 build redefine everything, while the native tests, which include by one path, passed. Keep the config out of headers; fill a logic class's settings in the one `.cpp` that already includes it.
- **Arduino's builder writes prototypes for every function above the first function in the sketch**, so a function taking a struct defined later in the `.ino` fails with "does not name a type". Declare such structs at the top of the file (or in a header).
- **ArduinoJson stores 181.2 as a float.** Compare numbers as the board shows them (a formatted string), not as doubles.

## State the device writes on the server
- **A QoS 1 resend can put an older write back as the retained value.** The ESP-IDF MQTT client sent each write twice; when a newer write went out in between, the broker kept the older one, and changes were lost until a reboot. Two things fixed it: the device writes its current value again whenever a live copy of its own topic differs from its last write, and changes made together go out as one write.
