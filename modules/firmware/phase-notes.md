# firmware phase-notes

Read only the section for the phase you're in. The hardware and library detail behind these (display, USB, wiring, sound, debugging a hang, behaviour over time, toolchain, retained state) is `lessons/firmware.md` in this skill's folder: read the parts that touch the work.

## Plan
- **A step that spans server and firmware is one spec with two implement sessions** and an explicit waiting point. The spec says which firmware work can start on today's contract and where the firmware session stops until Finn says the server part is pushed.
- **Read the schematic, not the vendor's example sketches, before claiming anything about pins.** On desk-bridge's board the sketches gave the right GPIO numbers but missed what else shares them: the speaker amp is always on, and one pin is both the touch interrupt and an I2S line. A plan built on them would have put a UART on the speaker and the touch controller. A vector PDF schematic can be rendered in overlapping tiles with `pdftoppm` (poppler) and read at full resolution, which beats OCR on screenshots; installing poppler needs Finn (sudo), so give him the command. **A vendor example that leaves a feature off is a clue, not a rule**: the board's music example never turns touch on, which with the schematic (the amp's LRCLK and the touch INT on one pin) looked like "they can't coexist". A probe showed touch working fine with sound playing; only the electrical detail (drive strength, who wins the wire) and the side effects (a held touch reported as repeated taps) needed design.
- **Probe the hardware during planning when it's on the bench**: a throwaway sketch per question, kept in `firmware/tools/` as a debug tool. E2's plan measured the encoders, the link and the host's sleep before writing a line of spec, and two of the three changed the design.
- **Measure what the UI can afford before designing it.** Finn ran the vendor's LVGL demo: static was fast, and anything moving (drag, scroll, animated charts) was slow. That one measurement set the design: no animations, no touch scrolling, lists move a row at a time by encoder.
- **Check whether flash writes disturb the device before planning any storage.** On an RGB panel with a bounce buffer they disable the cache and stall the refill, so that device keeps no state of its own: what it must remember lives on the server (retained messages, read back after a reboot), and there is no OTA. Ask early whether that holds for the next board.
- **Input hardware that arrives later goes behind a compile-time flag**: the UI for both cases is built now, the logic is unit-tested, and the flag is flipped for a look. **Widgets whose data doesn't exist yet are drawn as placeholders with sample data**, in their final places, so the layout can be judged; the spec says their pages may change once the real data exists.

## Implement
- **Before the first test, check that this machine can run the binaries it compiles.** On Finn's laptop Smart App Control blocks every unsigned executable built there (the `laptop` module); the first few runs got through by luck of its cloud check, then every rebuild was blocked. What cost nothing was running the native tests, and the mutation runner, on the Linux server over SSH: a small helper ships the firmware folder (never a `secrets.h`) to a scratch directory, pulls the host libraries in (ArduinoJson's headers) so the remote build needs nothing installed, and streams the output back.
- **A tiny test harness of our own** (a `CHECK` macro and named tests) avoids choosing a test library.
  - **A native test run that crashes hides every test after it, and prints no total.** A `CHECK` that fails and then indexes an empty vector (`writes[0]`) segfaults the whole program; the output just stops, with no "N run, M failed" line, and the tests that never ran look like they passed. After changing a rule many tests depend on, look for the final total line, not only for `FAIL`s, and fix the crashing test first.
  - **A `CHECK` that binds a const reference to a member of a temporary reads freed memory** (`CHECK_EQ(c.entries()[0].label, ...)`; under `-Werror=dangling-reference` it doesn't build). Copy the value into a local, or return it by value from a helper; likewise a pointer into a state object returned from a function dangles once the temporary is gone.
- **The board's headers define macros that break ordinary names.** `NAME_MAX` as a constant compiled natively and failed only in the real board compile. Compile the sketch for the board as well as running the native tests, and give constants a prefix of their own (`FANTASY_NAME_MAX`).
- **LVGL code can be syntax-checked on a machine with no board toolchain.** The UI files never reach the native tests, so a typo there used to show only in the laptop's 3-minute sketch compile. LVGL's release tarball (headers only matter) plus the sketch's own `lv_conf.h` is enough: `g++ -std=gnu++17 -fsyntax-only -DLV_CONF_INCLUDE_SIMPLE -I firmware/dashboard -I <lvgl-x.y.z> firmware/dashboard/src/ui/<file>.cpp`. Check it can fail (a file with a wrong call) before trusting a clean run. It is not the board's build (no Arduino or ESP-IDF headers, so `NAME_MAX`-style clashes still only show there).
- **The mutation runner is its own** (the Python module's is pytest-only): the same spec format, building and running the native tests.
  - **Give "could not build" its own exit code**, apart from "a test failed". A mutant that crashes the test program is a kill, and one that doesn't compile is not; with one shared non-zero code the runner called crashes "does not build" and hid kills.
  - **Make the mutants compile.** With `-Werror`, a mutation that leaves a variable, parameter or helper unused fails the build instead of changing behaviour: keep a use of it in the mutant (`(void)now;`, `|| true`, `&& false`).
  - **A mutant can print garbage**: decode the test output with `errors="replace"`, or one crashes the whole run.
- **Replay the server's real output through the parsers** (`lessons/testing.md`): the first replay of desk-bridge's own messages found that every real one would have been dropped. Capture only the live messages of a run you started (a retained copy on a dev broker is whatever an earlier run left there, possibly real), filter the topics the device never reads, and check the file holds no real data before it goes in the repo.
- **Time the redraw on the board** (`lv_refr_now()` in a temporary startup loop, read off serial) instead of judging by feel; remove the loop afterwards.
- **Check the networked build without flashing it**: compile a copy with a placeholder secrets file in a scratch directory. A vendor core's globals aren't free names (the ESP32 core already has `Network`, so a struct of that name in `secrets.h` stopped compiling).

## Verify
- **Flash the board for its checks without asking** when nothing is at risk (CLAUDE.md, *What not to ask*). Ask only for what needs Finn's hands or eyes, such as stopping a host helper that holds the port, or a round at the board.
- **A build cache keyed on file times breaks when the two machines' clocks disagree.** The laptop's clock ran 6 hours slow, so every edit looked older than the objects already built: the tests ran the old code and passed, and the flash wrote the old binary ("No changed sectors found"). When a green result follows a change, check that the change was built; fix the clock and force clean builds. A mutation runner that builds each mutant in a fresh copy is immune.
- **Watch the server side as another account while the device runs.** That is what showed a QoS 1 resend putting an older write back as the retained value (`lessons/firmware.md`); the unit tests could not.
- **When a check fails on the bench, measure before theorising.** A logging probe on the host (display and suspend events with times) showed the laptop waking itself 4 s into standby, even with the device unplugged: not a bug in the device. Two theories before it were wrong.
